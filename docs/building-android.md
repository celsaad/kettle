# Building the Android release on GitHub Actions

> **Live.** `.github/workflows/android.yml` builds the Play bundle on a GitHub runner instead of on
> EAS. EAS is not used by it at all, and `eas.json` is kept only for the one-off credentials access
> described below. The keystore setup here is a prerequisite — the workflow fails on the first run
> without it, deliberately and early.

## Why not EAS

The build itself is ordinary Gradle. What EAS added was a queue, and on the free tier the queue is
most of the wall clock — the build is over in the time it takes the job to start. `android/` is
generated by `expo prebuild` and gitignored, so a runner can regenerate it from scratch and get a
byte-identical project to what EAS would have built. Nothing about the managed workflow is given up.

What is genuinely lost: EAS's credential store (replaced by four repository secrets), its build
history (replaced by the Actions run list), and its remote caching. The last one is the real cost —
see "What it costs" below.

## One-time setup

### 1. Get the upload keystore out of EAS

**Play App Signing means the key on EAS is the *upload* key, not the app signing key.** Google holds
the signing key and re-signs every upload; the upload key only proves the upload is from you. That
matters twice over: losing it is recoverable (Play Console › Setup › App integrity resets it), and
so is leaking it. It is still a secret, just not an unrecoverable one.

```sh
npx eas credentials --platform android
```

Pick the `production` profile, then `Keystore: Manage everything needed to build your project` ›
`Download existing keystore`. It writes a `.jks` and prints the keystore password, key alias and key
password. **Write all three down before closing the terminal** — EAS shows them once here and the
`.jks` alone is useless.

This is a read of the credential store, not a build, so it returns immediately. It is also the last
thing in this repo that needs EAS.

### 2. Put it in four repository secrets

The keystore is binary, and secrets are text, so it goes in base64. On Windows:

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes("upload.jks")) | Set-Content keystore.b64 -NoNewline
```

```sh
gh secret set ANDROID_UPLOAD_KEYSTORE_BASE64 < keystore.b64
gh secret set ANDROID_UPLOAD_KEYSTORE_PASSWORD
gh secret set ANDROID_UPLOAD_KEY_ALIAS
gh secret set ANDROID_UPLOAD_KEY_PASSWORD
```

Then delete `keystore.b64` and keep the `.jks` somewhere you'd still have it after a laptop dies.
`*.jks` is gitignored, which stops the obvious accident and nothing else.

**The repository being public doesn't expose these.** Secrets are never given to a workflow triggered
from a fork, and this one is `workflow_dispatch` only, so the only way to run it is to already have
write access. Don't add a `pull_request` trigger to it — that is the change that would break the
property.

## Running it

Actions › Android build › Run workflow, or:

```sh
gh workflow run android.yml -f variant=aab
gh run watch
```

- **`aab`** — the Play upload. Every ABI, since Play splits the bundle per device.
- **`apk`** — sideloadable, `arm64-v8a` only. Three quarters less C++ to compile, and it will not
  install on an x86 emulator. It's signed with the same upload key, which is fine for a phone and
  is *not* enough for in-app purchases: `expo-iap` only resolves products in a build installed from
  Play (see `store/README.md` on licence testing).

The artifact is attached to the run for 14 days. Upload it to Play by hand — automating that needs a
service account JSON, which is a fifth secret with write access to the listing, and hasn't been worth
it for a release every few weeks.

**`versionCode` comes from `app.json`** via prebuild, and Play rejects a re-used one. `/bump` is what
increments it; the workflow doesn't, and `eas.json` has `autoIncrement: false` for the same reason.

## What it costs

Most of the wall clock is C++. `react-native-reanimated`, `react-native-worklets` and
`expo-modules-core` all ship sources rather than prebuilt `.so` files, so every ABI is compiled from
scratch; React Native's own core is a prebuilt Maven artifact and isn't part of this.

The Gradle cache (`gradle/actions/setup-gradle`) covers dependency downloads and, with
`--build-cache`, the Kotlin and Java compilation. It does **not** cover the CMake output: that lands
in `android/.cxx`, and `expo prebuild` regenerates `android/` on every run, so the NDK work is paid
in full each time.

If that becomes the problem, in rough order of payoff:

1. **ccache**, keyed on the lockfile — the only thing that attacks the actual cost. It needs
   `CMAKE_C_COMPILER_LAUNCHER` threaded through to the externalNativeBuild tasks, which is the fiddly
   part.
2. **A larger runner.** Paid, but linear, and the build is embarrassingly parallel across ABIs.
3. **Cache `android/.cxx` directly**, restoring it after prebuild. Fragile — it holds absolute paths
   and NDK version stamps, and a stale hit fails in ways that read as a compiler bug.

None of these are done. Measure a real run before picking one.

## The trap this is built around

The bare template signs release builds with the **debug** keystore, on purpose, with a comment saying
so. A build that keeps that produces a valid-looking `.aab` that Play rejects on upload — half an
hour after the mistake. `.github/scripts/inject-release-signing.mjs` repoints the release build type
at a real key and **fails the build rather than continuing** if it can't find what it expects in the
generated `build.gradle`, because the silent version of that failure is the expensive one.

The script patches `android/app/build.gradle` after prebuild instead of being an `app.json` config
plugin. A plugin would run on every local `expo prebuild` too, where there is no keystore and no
reason to diverge from the template; this is a release concern and lives with the release.

Its two anchors are `signingConfigs {` and the release build type's `signingConfig = signingConfigs.debug`.
If a future SDK renames either, the workflow fails loudly at that step — re-read the generated file
and update the two regexes. Passwords are read from the environment by Gradle rather than written
into the file, so the generated tree is safe to attach to a failed run.

The last step of the workflow prints the signing certificate's SHA-256. It should match the upload
certificate on Play Console › Setup › App integrity; if it matches the Android debug certificate
instead (`C=US, O=Android, CN=Android Debug`), the injection silently did nothing and the bundle is
not uploadable.
