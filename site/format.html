The library format

Kettle reads and writes one YAML file: your library. It's a plain, human-editable document, checked against a strict schema every time it's loaded or imported. This page is the full reference — read it, edit against it, or paste it at an assistant and ask for a program.

File shape

A library is a YAML mapping with four top-level keys. Every valid file declares its format version, then lists your exercises, the workouts that reference them, and any multi-week programs.

All three lists are required keys, even when empty. A file that adds two exercises and nothing else still needs workouts: [] and programs: [], or it is refused with a schema error naming the missing one. Their contents are what's optional, not their presence.

shape.yaml
version: 1

exercises: # the movements you do
  - id: back-squat
    name: Back Squat
    type: reps
    config: { ... }

workouts: # ordered blocks of exercises
  - id: lower-a
    name: Lower A
    blocks: [ ... ]

programs: [] # multi-week schedules (optional)

Order inside a list is meaningful: workout blocks and program days run top to bottom. Everything is referenced by id, so a workout points at an exercise's id rather than repeating its definition.

Exercises

An exercise is a single movement with a type that determines which config fields apply. These four keys are common to every exercise:

Field Type Required Meaning
id string yes Stable, unique key. Lowercase, hyphenated by convention. Used everywhere this exercise is referenced.
name string yes Display name shown in the app.
type enum yes One of the seven types below. Selects the runner and the valid config fields.
config mapping yes Type-specific settings — see each type.
notes string no Free text shown during the session. Cues, targets, reminders.

All durations are seconds and end in _sec; all weights are in kilograms, whatever units the app is set to display. A missing optional field falls back to the app's default rather than erroring.

Exercise types

There are seven types. Each is a shape of block with its own config fields. Fields marked optional may be omitted.

The repeat counts have an upper bound as well as a lower one. sets and rounds cap at 500 — including a circuit block's own rounds — and total_minutes at 1440. The session runner builds one step per set, per round and per interval before it draws anything, so an unbounded count is a workout that can't be started at all rather than a long one. 500 sets at 30 seconds each is over four hours — if you're anywhere near the ceiling, what you want is several workouts.

emom is bounded on what its two fields multiply out to rather than on either alone: the runner derives total_minutes × 60 ÷ interval_sec intervals, so the pair must come to at most 500. total_minutes: 60 with interval_sec: 1 is 3600 intervals and is refused, though neither number looks unusual by itself.

reps

Counted sets, for strength work. The runner takes a rep count, a load and an RPE per set.

config field Type Meaning
sets int 1–500 Number of working sets.
target_reps_min int > 0 Target reps, or the bottom of the range. Required.
target_reps_max int · optional Top of the range, ≥ target_reps_min. Omit for a fixed target.
target_weight number ≥ 0 · optional Suggested load, in kilograms. Omit for bodyweight.
rest_sec int ≥ 0 Rest between sets, in seconds.

hiit

Alternating work and rest intervals over a number of rounds, run as a live countdown.

config field Type Meaning
work_sec number > 0 Work interval length, in seconds.
rest_sec number ≥ 0 Rest interval between rounds, in seconds.
rounds int 1–500 Number of work/rest rounds.

emom

Every minute on the minute: start a fixed task at the top of each interval, rest the remainder.

config field Type Meaning
interval_sec number > 0 Length of each interval. Usually 60.
total_minutes number > 0, ≤ 1440 How long the whole block runs. This is the field that ends it — there is no rounds here.
target_reps int · optional Reps to hit within each interval.

amrap

As many rounds or reps as possible inside a single time cap.

config field Type Meaning
time_cap_sec number > 0 Total time cap, in seconds. The only field, and required.

timed_hold

Hold a position for a set duration — planks, hangs, wall sits, loaded carries.

Both targets are optional, and which you give decides when the set stops. The runner always counts up — the number on screen is the number written to your log — so the targets set the end, not the display. With hold_sec_min alone the hold ends there; with a range it ends at hold_sec_max, marking the minimum part-way along the bar and chiming as you cross it. Either way you get a 3-2-1 of ticks into the end, so you can prepare the dismount without looking at the phone.

Omit both and the hold never ends by itself — it counts until you tap Done set, which is how you write “hold as long as you can” and the only way a hold PR shows up in your history. hold_sec_max on its own is refused: a range needs both ends.

config field Type Meaning
sets int 1–500 Number of holds.
hold_sec_min number · optional Hold duration, or the bottom of the range. Omit it for a max-effort hold.
hold_sec_max number · optional Top of the range, ≥ hold_sec_min, and needs it. Same fixed-vs-range shape as reps.
rest_sec number ≥ 0 Rest between holds, in seconds.

cardio

A continuous effort tracked by time or distance.

config field Type Meaning
duration_sec number > 0 · optional Target duration, in seconds.
distance_meters number > 0 · optional Target distance, in metres.

Give either, both, or neither — an empty config: {} is valid and runs as a plain count-up stopwatch.

rest

A standalone rest block between efforts, timed to the second.

config field Type Meaning
duration_sec number ≥ 0 Length of the rest, in seconds. Note this is duration_sec, not rest_sec.

rest is not special-cased — it is an ordinary exercise you define once and reference from as many blocks as you like, overriding the duration per block where one rest should differ from the default.

Workouts

A workout is an ordered list of blocks, walked top to bottom by the session runner. Each block is tagged with a type: either a single exercise, or a circuit that cycles several exercises round-robin.

workout.yaml 
workouts:
  - id: calisthenics-a
    name: Calisthenics A
    blocks:
      - type: exercise
        exercise: pullups
      - type: exercise
        exercise: rest
        config: { duration_sec: 120 }   # this rest only
      - type: circuit
        id: finisher-rounds     # only needed if a program overrides it
        rounds: 3
        rest_between_exercises_sec: 15
        rest_between_rounds_sec: 60
        exercises:
          - exercise: pushups
          - exercise: l-sit
Field Type Required Meaning
id / name string yes Unique key and display name for the workout.
blocks list yes Ordered blocks, each type: exercise or type: circuit.
blocks[].exercise id exercise blocks The exercise this block runs.
blocks[].config mapping · optional — Only duration_sec is supported, and only meaningfully on a block referencing a rest exercise.
blocks[].rounds int 1–500 circuit blocks How many times the circuit cycles its members.
blocks[].exercises list circuit blocks At least two members, each { exercise: <id> }. A member may carry its own config on the same terms as blocks[].config above.
rest_between_exercises_sec number · optional — Rest between consecutive members within a round. Omit or set 0 for back-to-back work.
rest_between_rounds_sec number · optional — Rest after finishing all members, before the next round.

A circuit member runs once per round, whatever its own config says. The circuit's rounds is the only thing that repeats a member — a reps member's own sets is ignored inside a circuit, and its rest_sec is not inserted between visits. So pushups with sets: 3 in a 3-round circuit does 3 visits, not 9.

Supersets

A superset is a two-member circuit. There is no separate superset block type, and you don't need one — a circuit already runs its members round-robin, which is exactly what alternating A/B is. "3 × 8 chin-ups supersetted with 3 × 8 dips, 90s after each pair" is:

superset.yaml 
- type: circuit
  rounds: 3                      # the set count: 3 of each
  rest_between_exercises_sec: 0   # within the pair
  rest_between_rounds_sec: 90     # after each pair
  exercises:
    - exercise: chinups
    - exercise: dips

That runs chinups → dips → 90s → chinups → dips → 90s → chinups → dips, with no trailing rest after the last pair. The three fields map onto how you'd say it out loud:

You'd say Field
"3 sets of each" rounds: 3
"no rest between the two" rest_between_exercises_sec: 0 (or omit it)
"90 seconds after each pair" rest_between_rounds_sec: 90

Don't set an exercise's own rest_sec to 0 to express a pairing. Per the rule above, a circuit member's own sets and rest_sec are ignored — so chinups keeps whatever values make sense for it on its own, in some other workout. Editing them changes that exercise everywhere it's used, and the pairing still won't happen.

The mistake this replaces: writing the two exercises as separate type: exercise blocks and zeroing the first one's rest. That runs A, A, A, B, B, B — not a superset — and leaves the first exercise no rest at all between its own sets.

Both members get the same number of sets. Unequal pairs — 2 sets of A against 3 of B — can't be expressed as one circuit today; author the common rounds as a circuit and the odd sets as a separate block after it.

Programs

A program is a periodized wrapper around workouts you have already defined. Each entry in weeks carries a week number and the workout to run, and may layer overrides on top of the base definitions for that week only. Overrides are how a program progresses — add a set in week 3, cut the finisher in week 6 — without duplicating the workout.

An entry can also be a rest day: rest_day: true and no workout. It runs nothing and logs nothing, but it keeps its place in the rotation, so the home screen shows a rest card rather than queuing your next session the morning after the last one.

program.yaml 
programs:
  - id: pull-progression
    name: 6-Week Pull Progression
    weeks:
      - week: 1
        workout: calisthenics-a
        notes: Baseline — log where you land in each range.
      - week: 2
        workout: calisthenics-a
        overrides:
          - exercise: pullups
            config: { sets: 5 }
          - block: finisher-rounds
            config: { rounds: 2 }
      - week: 3
        rest_day: true
        notes: Nothing scheduled. Walk, stretch, or do neither.
Field Type Meaning
id / name string Unique key and display name.
weeks list The weeks of the program. Kettle queues the next one up.
weeks[].week int The week number, taken literally — see the note below.
weeks[].workout id · required unless rest_day The workout run that week. A week that isn't a rest day must name one.
weeks[].rest_day bool · optional true marks a scheduled day off: no workout, no overrides, nothing run and nothing logged. See the note below.
weeks[].day string · optional Freeform label (Monday, Push) for programs with more than one session a week. Each (week, day) pair must be unique. Omit it entirely for one session per week. The label is display text only — it is never parsed, and the days of a week run in the order you write them, so call them whatever you like but list them in the order you train them.
weeks[].notes string · optional Freeform note for the week.
weeks[].overrides list · optional A list, not a mapping. Each entry targets exactly one of exercise or block, plus a partial config.

Week numbers are literal, not a schedule to fill in. A program whose weeks jump 1 → 3 → 6 genuinely has three weeks, and the home screen walks 1 → 3 → 6 without ever offering 2, 4 or 5. Enumerate every week you intend to train.

Overrides don't carry forward. Each week resolves independently against the base definitions, so a change you want to persist from week 3 onward has to be repeated in every later week.

Write out every rest day, including the ones at the end of the week. Kettle spends one rest entry per calendar day, so a three-session week written as three entries rolls into the next week the day after your last session. Seven entries — three workouts and four rest days — make the week a week. A rest entry may carry day and notes, but not workout or overrides, and a program needs at least one week that runs something.

An exercise override uses that exercise's own config keys; a block override targets a circuit by its id and uses the circuit's keys (rounds, rest_between_exercises_sec, rest_between_rounds_sec). Give only the keys you're changing.

The merged result has to be valid on its own, and that is checked when the week runs — not on import. The patch itself only has to be a map of numbers and strings, which is what lets it be partial. So a week whose merged config the schema would refuse still imports, and is then ignored: that week runs the exercise exactly as exercises defines it, and the app marks the override as not applied.

Every rule in the type tables above applies to the merged whole, cross-field rules included — so { sets: 0 }, { rest_sec: -5 } and a { hold_sec_max: 60 } on a hold with no hold_sec_min are all dropped. Patch what you must, but patch it into something valid.

A key the target does not have is ignored rather than refused. { reps: 12 } on a reps exercise — whose field is target_reps_min — imports, changes nothing, and is shown as not applied. A block override may only target a circuit's own rounds, rest_between_exercises_sec and rest_between_rounds_sec; anything else is ignored the same way.

Import & merge

Importing a file does not replace your library — it merges into it, keyed by id. For each exercise, workout and program in the incoming file:

  • If the id is new, the item is added.
  • If the id already exists, the incoming definition replaces that item's definition.
  • Items you have that aren't in the file are left untouched.

Your session history is never part of the library file and is never affected by an import — it lives in a separate log of its own. That's what makes it safe to accept a file from anywhere: worst case, you replace some definitions you can edit back.

Stable ids are the contract. Keep an exercise's id constant across edits so overrides and history keep pointing at the right movement. Change the name freely; change the id only when you mean to create a different exercise.

A complete example

Everything above, in one valid file: five exercises covering four types, a workout with a rest override and a two-member circuit, and a program of three training slots closing on a rest day. This is checked against the app's own parser by the test suite, so it is known to import cleanly.

It is sized to be read in one screen, which is why it doesn't write its rest days out in full — copy the shape, not the schedule, and see the rest-day rule above. For four full programs, ready to import and edit, see the example libraries.

exercises.yaml 
version: 1

exercises:
  - id: pullups
    name: Pull-ups
    type: reps
    config:
      sets: 4
      target_reps_min: 5
      target_reps_max: 8
      rest_sec: 120
    notes: Stop 2 reps shy of failure.

  - id: pushups
    name: Push-ups
    type: reps
    config:
      sets: 3
      target_reps_min: 8
      target_reps_max: 15
      rest_sec: 60

  - id: l-sit
    name: L-sit
    type: timed_hold
    config:
      sets: 3
      hold_sec_min: 15
      hold_sec_max: 30
      rest_sec: 90

  - id: burpees
    name: Burpees
    type: hiit
    config:
      work_sec: 30
      rest_sec: 15
      rounds: 8

  - id: rest
    name: Rest
    type: rest
    config:
      duration_sec: 90

workouts:
  - id: calisthenics-a
    name: Calisthenics A
    blocks:
      - type: exercise
        exercise: pullups
      - type: exercise
        exercise: rest
        config: { duration_sec: 120 }
      - type: circuit
        id: finisher-rounds
        rounds: 3
        rest_between_exercises_sec: 15
        rest_between_rounds_sec: 60
        exercises:
          - exercise: pushups
          - exercise: l-sit

  - id: conditioning
    name: Conditioning
    blocks:
      - type: exercise
        exercise: burpees

programs:
  - id: pull-progression
    name: 4-Week Pull Progression
    weeks:
      - week: 1
        workout: calisthenics-a
        notes: Baseline — log where you land in each range.
      - week: 2
        workout: calisthenics-a
        overrides:
          - exercise: pullups
            config: { sets: 5 }
      - week: 3
        workout: conditioning
        notes: Deload the pulling, keep the engine.
      - week: 4
        rest_day: true
        notes: A week off. Start again at week 1 when you come back.

Using an assistant

Because this format is documented and schema-checked, you can have any AI assistant generate a program and paste the result straight into Kettle. A workable prompt:

“Here is the Kettle library format: [paste this page]. Write a valid version: 1 library for a 4-week push/pull/legs program, dumbbells only, sessions around 40 minutes. Use the seven exercise types where they fit. Output YAML only.”

Import the reply. Kettle validates it against the schema on your device and merges by id; anything invalid is reported rather than silently accepted. Then edit by hand — it's a file you can read.

To be exact: Kettle has no AI features and never calls a model. The assistant is something you bring; the app only ever reads the file you paste.
