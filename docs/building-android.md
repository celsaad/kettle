# Building the Android release on GitHub Actions

> **Live.** `.github/workflows/android.yml` builds the Play bundle on a GitHub runner, on every merge
> to `master` and on demand. The bundle is the **native shell** (`native/android`) hosting the RN app
> as an AAR, not the prebuilt RN app itself (M2 of the native migration). Releases up to 0.11.0 were
> the prebuilt app; the first shell release is M2's ship ticket. EAS is not used by
> it at all, and `eas.json` is kept only for the one-off credentials access described below. The
> keystore setup here is a prerequisite — without it the workflow fails on the first run,
> deliberately and early, which for a merge trigger means every merge until it's done.

## The pipeline

Two Gradle builds, one after the other, in one job:

1. **The RN app, as an AAR.** `expo prebuild` regenerates the gitignored `android/` tree, and
   `publishBrownfieldReleasePublicationToMavenLocal` builds it as a library — native code, the Expo
   modules and the JS bundle from this commit — into the runner's `~/.m2`. This is the expensive half:
   it is the prebuilt app's whole native build.
2. **The shell, as an `.aab`.** `native/android`'s `:app:bundleRelease` builds the Compose shell around
   that AAR and signs it with the upload key. Its application id, `versionCode` and `versionName` are
   read from `app.json`, so the bundle is `com.casco.kettle` at the same version the prebuilt app would
   have been, and installs over a Play copy in place.

Only the release half of the AAR is published. `scripts/native-dev.ps1` publishes both halves, for a
reason that only applies to a mavenLocal that already holds the other one; the runner's starts empty,
and the debug half would be a second full C++ build for nothing.

The prebuilt app's own `:app` is never built, so nothing in `android/` is signed any more and the
script that used to patch its signing config is gone.

## Why not EAS

The build itself is ordinary Gradle. What EAS added was a queue, and on the free tier the queue is
most of the wall clock — the build is over in the time it takes the job to start. `android/` is
generated by `expo prebuild` and gitignored, so a runner can regenerate it from scratch, and the shell
is an ordinary Gradle project checked into the repo.

What is genuinely lost: EAS's credential store (replaced by four repository secrets), its build
history (replaced by the Actions run list), and its remote caching. The last one is the real cost —
see "What it costs" below.

## One-time setup

### 1. Get the upload keystore out of EAS

**Play App Signing means the key on EAS is the *upload* key, not the app signing key.** Google holds
the signing key and re-signs every upload; the upload key only proves the upload is from you. That
matters twice over: losing it is recoverable (Play Console › Setup › App integrity resets it), and
so is leaking it. It is still a secret, just not an unrecoverable one.

```sh
npx eas credentials --platform android
```

Pick the `production` profile, then `Keystore: Manage everything needed to build your project` ›
`Download existing keystore`. It writes a `.jks` and prints the keystore password, key alias and key
password. **Write all three down before closing the terminal** — EAS shows them once here and the
`.jks` alone is useless.

This is a read of the credential store, not a build, so it returns immediately. It is also the last
thing in this repo that needs EAS.

### 2. Put it in four repository secrets

The keystore is binary and a secret is text, so it goes in base64. PowerShell, since that's what this
is run from — `gh secret set NAME < file` is the documented form and PowerShell has no `<` redirect,
so the encode and the upload are one expression instead and no `.b64` is left lying about:

```powershell
gh secret set ANDROID_UPLOAD_KEYSTORE_BASE64 --body ([Convert]::ToBase64String([IO.File]::ReadAllBytes("upload.jks")))
```

The other three take no file and prompt, so they are the same everywhere. Their values come from what
the download printed: `keystorePassword`, `keyAlias` and `keyPassword` in EAS's `credentials.json`
naming.

```powershell
gh secret set ANDROID_UPLOAD_KEYSTORE_PASSWORD
gh secret set ANDROID_UPLOAD_KEY_ALIAS
gh secret set ANDROID_UPLOAD_KEY_PASSWORD
```

Confirm the alias and the keystore password against the file rather than against what you copied — a
wrong alias fails half an hour into a build. `keytool -list -v -keystore upload.jks` prompts for the
keystore password and prints `Alias name:`; `keytool -certreq -keystore upload.jks -alias <alias>` is
the non-destructive way to check the *key* password, which `-list` never touches.

Keep the `.jks` somewhere you'd still have it after a laptop dies.
`*.jks` is gitignored, which stops the obvious accident and nothing else.

**The repository being public doesn't expose these.** Secrets are never given to a workflow triggered
from a fork, and this one runs only on a push to `master` or on a manual dispatch — both of which
already require write access. Don't add a `pull_request` trigger to it: that is the single change
that would break the property, and it wouldn't buy the cache warming it looks like it would (see
below).

### 3. Record the app signing certificate

**Play Console › Setup › App integrity** prints two SHA-256 fingerprints. Both belong here, and
confusing them is the whole reason they are written down together rather than looked up separately
each time:

| | SHA-256 | What it is |
| --- | --- | --- |
| **Upload certificate** | `48:0A:30:FE:53:E5:84:D0:AF:17:1F:1E:89:39:57:C2:86:12:E5:3E:90:29:44:38:36:5F:6E:E5:AA:0A:AA:54` | What this workflow signs with. Every `.aab` and `.apk` built here carries it. Play strips it. |
| **App signing certificate** | `_(fill in from the Console)_` | What Play re-signs with, and therefore what every installed copy actually carries. |

The upload row is the certificate on the 0.11.0 release bundle, read from the log of the `master`
run that built it, and is pinned in `android.yml` as `UPLOAD_CERT_SHA256`. Check it against the
Console once; if the two ever disagree, the Console wins and both copies here are wrong.

Neither is a secret — they are public certificates, which is why they can live in the repo. It is the
private keys they belong to that differ: Google holds the app signing one and will never release it.

They earn their place here twice:

- **The workflow's "Check the signing certificate" step** fails unless the build carries the *upload*
  row. That is the check for a build that came out unsigned or signed with some other key, which
  produces a perfectly valid-looking file that Play rejects half an hour later.
- **`/release` checks a candidate APK against the *app signing* row** before it is attached to a
  GitHub Release. An APK matching the upload row instead is the one artefact that must never be
  published — see the signing entry in [`decisions.md`](decisions.md).

## When it runs

**On every merge to `master`**, skipping prose-only changes (`docs/`, `site/`, `store/`, any `.md`).
That build is doing two jobs at once: it is the only full release build CI runs — `ci.yml`'s
`native-app` job builds the shell too, but against a cached arm64 AAR — so it's what catches a
dependency bump breaking the bundle; and it leaves a warm ccache behind for the next one.

**Manually**, when you want an `.apk` or a build at a bumped `versionCode`:

```sh
gh workflow run android.yml -f variant=aab
gh run watch
```

A dispatch with `--ref <branch>` runs that branch's copy of the workflow, which is how a change to the
pipeline itself gets its first run before it merges.

- **`aab`** — the Play upload. Every ABI, since Play splits the bundle per device.
- **`apk`** — sideloadable, `arm64-v8a` only. Three quarters less C++ to compile, and it will not
  install on an x86 emulator. It's signed with the same upload key, which is fine for a phone and
  is *not* enough for in-app purchases: `expo-iap` only resolves products in a build installed from
  Play (see `store/README.md` on licence testing).

  **It is also not the APK that gets published**, and both reasons are silent. The upload-key
  signature makes it a different app from a Play install, so nobody can move between the two without
  uninstalling and losing their log; and `arm64-v8a` alone leaves out devices the Console's universal
  APK covers. The public artefact is *downloaded* from Play rather than built here — see the signing
  entry in [`decisions.md`](decisions.md), and `/release`.

Both variants are the same signed release build; the merge trigger produces an `.aab`. The artifact
is attached to the run for 14 days, named by run number rather than by version — only a release commit
bumps `versionCode`, so a week of merge builds are all `kettle 0.3.0 (6)` and nothing inside the file
distinguishes them.

Upload to Play by hand. Automating it needs a service account JSON, which is a fifth secret with
write access to the listing, and hasn't been worth it for a release every few weeks.

**`versionCode` comes from `app.json`**, which the shell's `app/build.gradle.kts` reads, and Play
rejects a re-used one. The shell continues the prebuilt app's line rather than starting its own,
since it replaces that app in place. `/bump` is what increments it; the workflow doesn't, and
`eas.json` has `autoIncrement: false` for the same reason.

## What it costs, and what warming it actually means

Most of the wall clock is C++, all of it in the AAR half. `react-native-reanimated`,
`react-native-worklets` and `expo-modules-core` all ship sources rather than prebuilt `.so` files, so
every ABI is compiled from scratch; React Native's own core is a prebuilt Maven artifact and isn't
part of this. The shell itself is Kotlin and resources, and adds a few minutes.

Two caches, covering different things:

- **Gradle** (`gradle/actions/setup-gradle`, plus `--build-cache`) — dependency and wrapper
  downloads, and the Kotlin and Java compilation of both builds.
- **ccache** — the C++, which is the expensive half. It has to be ccache rather than a cache of the
  build directory: the NDK output lands in `android/.cxx`, `expo prebuild` regenerates `android/`
  every run, and `externalNativeBuild` tasks aren't Gradle-cacheable anyway. ccache works at the
  compiler, below all of that. `ci.yml`'s `native-app` job restores this same cache, read-only, when
  its own AAR cache misses.

**A prior build on a branch does not warm master.** Actions caches are scoped: a branch can read the
default branch's caches, but the default branch cannot read a branch's. So a "pre-build on the PR"
stage would populate a cache only that PR can use, and the post-merge build would still start cold.
The only thing that warms the merge build is the *previous* merge build — which is why the trigger is
`push: master` and not `pull_request`.

Three things to know about the ccache setup — what it buys, and the two knobs that will eventually be
the reason it stops buying it:

- **What it's actually worth, measured** (on the prebuilt app's own build, before the shell; the C++
  is the same). Two back-to-back `apk` runs off an identical tree: cold 13m13s at a 2% hit rate, warm
  11m14s at **30%**. Real, and well short of what an unchanged source tree ought to give — 204 of 293
  compilations still missed, with the preprocessed-mode fallback salvaging none of them, so the inputs
  genuinely differ rather than just their paths. Codegen output and the absolute include paths into
  Gradle's extracted prefab directories are the two suspects; `CCACHE_DEBUG=1` dumps the reason per
  miss and is where to start. Not chased yet.
- **The stats step is not decoration**, and read `Cacheable calls` before the hit rate. That line is
  what proves `CMAKE_C_COMPILER_LAUNCHER` is still reaching the CMake invocations: if it stopped,
  ccache would record *no calls at all* rather than a run of misses. CMake takes it as the default
  for `CMAKE_<LANG>_COMPILER_LAUNCHER`, and a module setting that variable explicitly would win over
  it. The fallback is injecting `cmakeArgs` in the prebuild patch, which is worse and hasn't been
  needed.
- **The sloppiness settings are load-bearing.** `time_macros` and the `include_file_*` pair are what
  stop the NDK headers missing on every run, and `pch_defines` covers reanimated's generated stub
  PCH. `base_dir` and `hash_dir=false` keep the regenerated absolute build path out of the hash.
  Tightening any of them turns the cache silently cold rather than breaking anything.

If it's still too slow after that, the remaining levers are a **larger runner** (paid, but linear,
and the build parallelises well across ABIs) and **dropping ABIs** — `x86`/`x86_64` exist for
emulators, and Play would serve a bundle without them to nobody real. Neither is done.

## How signing works, and the trap it's built around

The shell's `app/build.gradle.kts` gives the release build type an `upload` signing config **only when
`KETTLE_UPLOAD_KEYSTORE` is set**, reading the path and the three passwords from the environment at
Gradle time. Nothing is written into a file, so a failed build's tree is safe to attach to a run.
Everywhere else — a local `:app:build`, `ci.yml`'s `native-app` job — release builds come out
unsigned, which is harmless: an unsigned file installs nowhere and Play refuses it.

The debug build type keeps Expo's public template debug key, as before. It signs nothing that leaves
a developer's machine.

**The trap is a build that looks signed and isn't, or is signed with the wrong key.** Both produce a
valid-looking `.aab` that Play rejects on upload, half an hour after the mistake; the prebuilt app's
template had one built in, signing release with the debug keystore on purpose. So the workflow doesn't
trust the build: its "Check the signing certificate" step reads the certificate off the output
(`keytool` for an `.aab`, `apksigner` for an `.apk`) and **fails the run** unless it is
`UPLOAD_CERT_SHA256`. A missing secret, a renamed environment variable or a wrong alias all end there,
before anything is uploaded.

That pinned value changes only if the upload key itself is reset in the Console. Changing which key
signs what is the one mistake in this repo that can't be fixed for people who already installed — read
the signing entry in [`decisions.md`](decisions.md) before touching it.
